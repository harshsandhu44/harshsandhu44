## The problem

Following a Formula 1 weekend means hopping between a timing screen, a weather site, a standings table and a results archive. I wanted all of it in one place, and I wanted it to cost nothing to run.

pitwall is that place. It shows the next weekend with a countdown and the weather at the circuit, live timing while a session is on track, and a replay of any session since 2023 on the same dashboard. It runs entirely on free tiers plus an OpenF1 sponsor account.

<Shot n={2} />

## What I built

- **A static Next.js app** with home, live, calendar, standings, race-weekend, driver, team and replay pages. Every page takes a query parameter for the season instead of a path segment, so the whole site stays a plain static export.
- **A Cloudflare Worker API** that fetches from OpenF1, Jolpica, Open-Meteo and RainViewer, validates and normalizes the data, and returns one response envelope that says whether the data is fresh, stale or unavailable, and why.
- **Live timing** with a timing tower, race-control messages, track weather and a track map with cars moving smoothly between polls.
- **Session replay** with playback controls and driver comparison, on the same panels as live.
- **Race-weekend weather**: observed radar, a cloud and wind map, and a forecast for each session.
- **A dashboard of panels** you can drag, resize and hide, with a menu for keyboard and touch users and layouts saved in the browser.

## Key decisions

<Shot n={3} />

### One shared live connection

OpenF1 streams live data over MQTT. Rather than have each visitor connect, a single Durable Object holds the only connection: it opens when the first person asks for live data, loads the session so far, applies messages as they arrive, and disconnects two minutes after the last request. mqtt.js doesn't run on Workers, so I wrote a minimal MQTT 3.1.1 client for it. One viewer polling through a two-hour race costs about 2,400 Worker requests, against a free limit of 100,000 a day.

### Always serve a last good copy

The Workers cache is per data centre, so every successful upstream response is also written to D1. A cache miss checks D1 before calling the upstream, and an expired copy is served straight away, marked stale, while a fresh one is fetched in the background. Each upstream gets refreshed about once per freshness window worldwide, and a request only waits on an upstream when no copy exists at all.

### Live and replay share one engine

Live timing builds its timing tower with the same functions as replay, so the two can't disagree. Replays load car positions in 60-second windows with a second of overlap at each end, so interpolation never needs a neighbouring window. The browser keeps the current window and the next two. Cars are only interpolated between samples less than a second apart; past that they're shown as stale rather than guessed.

<Shot n={4} />

### Move off Jolpica for 2023 onward

Jolpica limits requests by IP, and every Worker reaches it from the same shared Cloudflare IP, so the deployed API was often refused. Everything from 2023 on now comes from OpenF1, broken into small units that are cached separately. Jolpica only fills older seasons, on demand. I checked the 2026 standings, points progression and wins against Jolpica, and they're identical.
